# Журнал решений

## 2026-09-10 Security foundation

- Прямые `FileField.url` не являются механизмом авторизации. Все чувствительные вложения выдаются через Django endpoints, которые проверяют доступ к родительскому объекту.
- Общесистемная документация остаётся доступной всем аутентифицированным пользователям по существующему endpoint; вложения обращений наследуют org scope, сообщения — membership, задачи — admin role.
- Production-конфигурация обязана завершаться ошибкой без отдельных сильных `SECRET_KEY` и `JWT_SECRET`. HTTPS, secure cookies и HSTS включены по умолчанию и могут быть явно изменены только окружением для контролируемого TLS-терминатора.
- База PostgreSQL не публикуется на host в production compose. `media` и `exchange` хранятся в именованных volumes.
- `PROMPT_v3` используется как backlog UX, но не расширяет ТЗ там, где вводит таск-трекер, realtime или социальные функции без подтверждения бизнес-процесса.

## 2026-09-10 Atomic exchange import

- Файл обмена является минимальной атомарной единицей: ошибка XSD, ФЛК или сохранения любой строки откатывает все изменения этого файла, включая `XmlFiles`.
- Ошибочный файл архивируется, а FLCP и `ImportLog` сохраняются вне откатанной бизнес-транзакции, чтобы участник обмена получил диагностический протокол.
- XML обрабатывается parser с `resolve_entities=False`, `no_network=True`, `huge_tree=False`; UI и автоматический импорт отклоняют файлы больше 20 МБ.
- Артефакты с повторными именами получают уникальный суффикс. Существующие входные файлы, архивы и протоколы никогда не перезаписываются.

## 2026-09-10 RBAC capability boundary

- Пользователь без назначенной роли не может создавать или изменять обращения и загружать файлы обмена, даже если он аутентифицирован и относится к ТФОМС.
- ОП1 и СП1 регистрируют обращения и выполняют первичную переадресацию. ОП2, СП2 и СП3 могут обрабатывать доступные им обращения, но не получают права первичной регистрации только из-за аутентификации.
- Администратор и superuser имеют служебный доступ; администратор контакт-центра не получает права изменения обращений без отдельной рабочей роли.
- Чтение журнала, обмена и отчётности также проходит через capability policy: аутентификация без признанной роли недостаточна. Проверка роли предшествует ограничению по организации.
- Пользователь может состоять в нескольких ролевых группах; решения принимаются по всему множеству ролей, а не по первой группе из QuerySet.

## 2026-09-10 Lifecycle обращений

- Статус хранится явно, чтобы переходы были проверяемыми и отражались одинаково в UI, импорте и серверных действиях.
- Состояния: зарегистрировано, в работе, переадресовано, предварительный ответ, закрыто. Закрытое обращение терминально: редактирование, новый ответ, вложение и переадресация запрещены на сервере.
- Закрытие атомарно требует одновременно дату и исход; дата закрытия не может предшествовать дате поступления.
- Плановый срок также не может предшествовать поступлению; lifecycle-статус ограничен системным перечнем на уровне БД. Legacy-даты, нарушающие хронологию, при миграции выравниваются по дате поступления, неизвестный legacy-статус переводится в `registered`.
- Код организации сотрудника — часть tenant security boundary, поэтому ограничен текущим реестром ORGS на уровне БД. Неизвестные legacy-коды не угадываются: связанная учётная запись деактивируется до технической нормализации.
- Для существующих записей миграция выводит статус из даты закрытия, предварительных ответов и реквизитов переадресации.

## 2026-09-10 Семантика прочтения сообщений

- Просмотр диалога показывает список тем и не считается прочтением их содержимого. Сообщения отмечаются прочитанными только при открытии конкретной темы.
- Счётчики вычисляются агрегатами БД, а отметки создаются пакетно через промежуточную M2M-таблицу без лимита в 500 сообщений.

## 2026-09-10 Доступность таблицы журнала

- Основной переход из строки имеет настоящий `a[href]`; клик по строке остаётся прогрессивным улучшением через `data-href`, а не единственным способом навигации.
- Серверные ссылки сортировки сохраняют активные фильтры, сбрасывают только страницу и публикуют направление через `aria-sort`.

## 2026-09-10 Защита запуска заданий

- Право на выполнение захватывается одним условным `UPDATE ... WHERE status != running`; это атомарно между web-worker и внешним планировщиком без удержания долгой транзакции.
- Повторный запуск не создаёт `TaskRun` и сообщает «уже выполняется». После штатного завершения тот же владелец запуска записывает итоговый статус и лог.

## 2026-09-10 Счётчик ошибок аутентификации

- Инкремент, ограничение максимумом и установка постоянной блокировки выполняются одним условным SQL UPDATE. Решение не зависит от устаревшего значения модели в памяти и не теряет параллельные попытки.
- После достижения лимита счётчик не растёт; разблокировка остаётся только явным действием администратора согласно ТЗ.

## 2026-09-10 Lifecycle событий аудита

- Точечные события завершаются при создании с нулевой длительностью; HTTP-события сохраняют измеренную длительность; длительные операции явно создаются как `pending` и завершают ту же запись.
- Завершение без переданной длительности рассчитывает её по `started_at`, поэтому `finished_at` и `duration_ms` больше не расходятся.
- Проверка capability централизована в `apps.core.policy`; object scope организации остаётся отдельным обязательным уровнем контроля.

## 2026-09-10 Сквозной вход по временному токену

- Endpoint только принимает ранее выданный краткоживущий JWT и не публикует операцию выпуска токена. Поддерживаются POST-поле и `Authorization: Bearer`; токен не попадает в URL, серверный аудит или ответ.
- GUID из `sub` разрешается через отдельный `EmployeeRepository`, чтобы источник единого репозитория можно было заменить без изменения протокола token exchange.
- Сессия создаётся только для существующей, активной и незаблокированной учётной записи. Redirect разрешён только на локальный безопасный адрес; ответ запрещено кешировать и передавать как referrer.
- JWT обязан содержать `sub`, `aud`, `jti`, `iat` и `exp`; `jti` является UUID и уникален для каждого выпуска. Идентификатор атомарно фиксируется при успешном обмене, поэтому повторное предъявление токена не создаёт новую сессию даже при параллельных запросах.
- Просроченные использованные идентификаторы удаляются при последующих успешных обменах. Токен не помечается использованным, если учётная запись отсутствует, неактивна или заблокирована.
- Ожидаемая аудитория задаётся единственным параметром `JWT_AUDIENCE` и одинаково применяется при внутреннем выпуске и внешней проверке; токен для другой информационной системы отклоняется.

## 2026-09-10 Персональная раскладка реестра

- Порядок ключей в `UserTableViewPref.columns` является одновременно порядком и набором видимых колонок; реестр не пересортировывает его по системному каталогу.
- Групповые заголовки вычисляются после применения персонального порядка, поэтому `colspan` соответствует фактически соседним видимым колонкам. Фиксация применяется к первой колонке уже персональной раскладки.

## 2026-09-10 Восстановление планировщика

- Каждый цикл scheduler сначала закрывает зависшие запуски старше `TASK_STALE_AFTER_SECONDS` (по умолчанию час). Строка задания повторно проверяется под `select_for_update`, чтобы recovery не пересёкся с новым claim.
- Задание, незавершённые `TaskRun` и соответствующее pending-событие получают единый failed-результат и время завершения. После восстановления применяется обычный интервал, исключающий немедленный бесконечный перезапуск.
- Планировщик поставляется отдельным Compose-сервисом и вызывает идемпотентную management-команду раз в минуту; атомарный claim сохраняет корректность при нескольких экземплярах.

## 2026-09-10 Печать реестра

- Печатный список повторно использует серверные фильтры, org scope, сортировку и персональный набор/порядок колонок реестра; отдельного менее защищённого запроса данных нет.
- Печать всегда начинается с первой строки выборки и ограничена 500 записями, чтобы случайный широкий фильтр не создавал неограниченный ответ. Полное машинное извлечение остаётся задачей отчётного экспорта.
- Серверная пагинация сохранена вместо infinite scroll: она предсказуема для клавиатуры, URL-навигации и ассистивных технологий.

## 2026-09-10 Назначение ролей пользователям

- Пользовательские формы назначают только семь зарегистрированных доменных ролей; произвольные Django-группы не являются скрытым механизмом выдачи доступа.
- Роли ОП и административные роли разрешены сотрудникам ТФОМС, роли СП — сотрудникам СМО. Несовместимая комбинация отклоняется до сохранения пользователя.
- UI-матрица генерируется из `CAPABILITY_ROLES`, а не дублирует правила вручную; при изменении серверной policy отображение меняется вместе с ней.

## 2026-09-10 Сортировка связанных строк DataTable

- `data-sort-group` объявляет несколько строк одной логической записью. Сортируется значение первой строки, после чего вся группа переносится целиком; это сохраняет логи задачи и детали события рядом с владельцем.
- Тип сортировки задаёт заголовок колонки, а ISO-значения дат передаются через `data-value`. Служебные колонки явно исключаются атрибутом `data-no-sort`.
- Клиентские заголовки сортировки получают focus, `aria-sort` и обработку Enter/Space; серверные заголовки журнала продолжают использовать обычные ссылки.

## 2026-09-10 Query string пагинации

- Все серверные пагинаторы используют встроенный тег Django `querystring`, который заменяет текущее значение `page`, сохраняя остальные фильтры. Ручная конкатенация параметров удалена из журнала, пользователей, событий и новостей.

## 2026-09-10 Воспроизводимость контейнера

- Сбор статических файлов является build-time операцией и выполняется с базовыми настройками без production-секретов. Строгая проверка секретов остаётся только на runtime.
- `psycopg[binary]` содержит собственный libpq, поэтому лишний apt-слой удалён. Первый dependency-слой устанавливает lockfile без локального проекта, который устанавливается после копирования исходников.
- Scheduler ждёт healthy-состояния web, то есть завершения миграций и старта Gunicorn. CI проверяет миграционный drift, production settings, Compose и собирает образ для каждого PR; публикация образа остаётся только для `main`.

## 2026-09-10 Комплект эксплуатационной документации

- Runbook, инструкция пользователя, логическая структура БД и форматы обмена версионируются рядом с кодом, чтобы команды и ограничения проходили review вместе с реализацией.
- Backup считается согласованным только при наличии дампа БД и файловых volumes из одного окна обслуживания; процедура восстановления явно отмечена как разрушающая текущее состояние цели.
- Неполученные Приложения №1–10 и XSD отмечены как граница подтверждённого контракта, а не заменены вымышленной спецификацией.

## 2026-09-10 Производительность горячих выборок

- Глобальный badge непрочитанных считается одним `COUNT DISTINCT` по диалогам. Список диалогов получает идентификатор последнего сообщения коррелированным подзапросом и загружает сами сообщения одним bulk-запросом; количество SQL-запросов больше не зависит от числа диалогов.
- Поиск диалогов по названию, участнику и тексту сообщения перенесён в SQL. Это исключает загрузку всей истории сообщений в Python для каждого диалога.
- Индексы добавлены только под подтверждённые запросы: организация сотрудника, даты/сроки обращений, организация и дата импорта, дата/результат события, последнее сообщение темы и выборка scheduler. Подстрочный поиск не маскируется бесполезным B-tree индексом и требует отдельного PostgreSQL trigram-решения при подтверждённой нагрузке.
- Счётчики просмотров новостей и скачиваний документов инкрементируются выражением `F()` непосредственно в БД, чтобы параллельные запросы не перезаписывали результат друг друга.
- Обложки новостей ограничены 10 МБ и allowlist форматов на уровне поля модели; встроенный `ImageField` дополнительно проверяет фактическое содержимое в пользовательской форме.
- Rich-text ссылки принимают только HTTP(S) с явным host, `mailto:` с адресом или локальный путь с одним `/`. Protocol-relative `//host` не считается локальным URL.

## 2026-09-11 Визуальная оболочка и реестр

- Основная навигация остаётся одной строкой и горизонтально прокручивается на узких экранах: это сохраняет стабильную высоту страницы и порядок разделов без скрытого hamburger-меню.
- На экране журнала заголовок сокращён до рабочего контекста, рядом показано количество найденных записей. Действия разделены на фильтрацию, сервисные операции и одно целевое создание обращения.
- Широкая таблица сохраняет полный доменный набор колонок, но контейнер получил keyboard focus, явное доступное имя и управляемую горизонтальную прокрутку. На мобильной ширине основной CTA поднимается первым.
- Таблицы используют единую плотную типографику, tabular numerals, спокойное чередование строк и цветную боковую метку вместо сплошной статусной заливки. Длинный УНр больше не переносится посимвольно; для широких реестров предусмотрен осознанный горизонтальный scroll.
- В шапке показывается доменное имя роли, а не внутренний числовой код. Несуществующий preload шрифта удалён: портал не создаёт 404 на каждом экране и честно использует системный fallback-стек.

## 2026-09-11 Карточка и форма обращения

- Карточка группирует реквизиты в двухколоночную сетку смысловых секций на широком экране и в последовательный поток на мобильном. Внутри секции пары «название — значение» разделены спокойными линиями вместо множества вложенных карточек.
- Возврат и печать остаются вторичными действиями, переадресация — контекстным, редактирование — единственным основным. Статус расположен рядом с номером и не конкурирует с кнопками.
- Длинная форма использует нумерованные разделы с кратким пояснением. Обязательность выводится из нативного атрибута поля, поэтому визуальная звёздочка синхронизирована с серверной формой; панель сохранения остаётся доступной у нижней границы экрана.

## 2026-09-11 Интерфейс сообщений

- На узком экране создание или текущая тема показываются перед каталогом диалогов: пользователь сначала видит активную работу, а список остаётся доступен ниже без отдельного скрытого меню.
- Пустой экран объясняет следующий шаг вместо технического описания требований. Заголовки диалога и темы используют общий компонент с контекстной обратной ссылкой, статусом и участниками.
- Непрочитанный диалог выделяется цветной боковой меткой, согласованной с реестрами, без заливки всей карточки.

## 2026-09-11 Унификация служебных разделов

- Отчётность, автоматизированные задания, новости и документация используют общий заголовок: короткий рабочий контекст, название, пояснение и только один счётчик либо основной CTA.
- Ссылки на номера разделов PRD убраны из пользовательских пояснений. Ограничение области данных СМО показывается как заметка о текущем scope, а не как тревожное предупреждение.
- Карточка новости больше не является внешней ссылкой с вложенными ссылками и формами: отдельная ссылка ведёт в материал, а административные действия остаются независимыми валидными элементами управления.

## 2026-09-11 Административные экраны

- Создание учётной записи и загрузка файла обмена вынесены из фильтров в заголовок раздела: фильтрация больше не конкурирует с основным действием.
- События показывают число найденных записей, а выгрузка остаётся вторичным действием после применения фильтров. Настройки описывают пользовательский результат вместо ссылок на пункты ТЗ.
- Формы пользователей, заданий, новостей и таблиц используют общий контекстный заголовок и предсказуемый возврат. Английская подпись `Stop` заменена доменным действием «Отключить».

## 2026-09-11 Вход и завершающие рабочие сценарии

- Неавторизованному пользователю не показывается меню защищённых разделов: экран входа сохраняет бренд, но фокусируется только на аутентификации.
- Загрузка обменного файла заранее сообщает допустимые имена, форматы и размер. Экран результата отделяет реквизиты загрузки от строк форматно-логического контроля и предлагает повторную загрузку как основное продолжение.
- Переадресация использует тот же заголовок формы, что остальные карточки; сохранение является основным действием, сопроводительное письмо — вторичным печатным результатом.

## 2026-09-11 Печатные представления

- Сопроводительное письмо, карточка и реестр используют общий экранный образ бумажного листа и отдельную панель печати, которая не попадает в результат.
- При печати оболочка портала, навигация, уведомления и preview-подсказки скрываются глобально; sticky-заголовки таблиц становятся статичными, а смысловые карточки не разрываются между страницами.
- Содержимое и юридические формулировки не менялись: этап затрагивает только композицию, типографику и print CSS.

## 2026-09-11 Кеш зависимостей контейнера

- Оба шага `uv sync` используют общий BuildKit cache mount. Загруженные wheels переживают перестроение слоя и повторный запуск после временного сетевого сбоя, но не попадают в итоговый runtime-слой.
- Разделение dependency/project install сохранено: изменение исходников по-прежнему не инвалидирует базовый слой сторонних зависимостей.
- Dependency install получает увеличенный timeout и десять повторов только внутри build-step. Это компенсирует кратковременные TLS-обрывы внешнего package registry, не меняя сетевые параметры приложения в runtime.

## 2026-09-11 Целостность протокола обмена

- `ImportLog.org`, `kind` и `status` являются закрытыми системными справочниками и проверяются базой данных, а не только формами Django.
- Повреждённая legacy-запись не должна останавливать production migration: неизвестная организация изолируется в scope ТФОМС, неизвестный статус трактуется как ошибка, вид файла восстанавливается по расширению XLSX или префиксу users; всё остальное классифицируется как обращение с ошибочным статусом.

## 2026-09-11 Целостность системного аудита

- Незавершённое событие хранит одновременно пустые `finished_at` и `duration_ms`; завершённое обязано иметь оба значения и непротиворечивую хронологию.
- Неизвестные значения типа или результата не сохраняются как новые скрытые категории: база принимает только системные перечисления, а legacy-аномалии явно маркируются `other/failed`.
- Исправление legacy-аудита сохраняет строки: пустой модуль получает техническое имя `unknown`, обратное завершение выравнивается по началу, неполная пара переводится в pending либо получает нулевую длительность.

## 2026-09-11 Строгая политика стилей портала

- Пользовательские шаблоны не содержат inline `style` и event-handler атрибутов, поэтому `style-src 'unsafe-inline'` удалён из CSP без изменения отображения.
- Стили портала загружаются только с текущего origin. Django Admin остаётся вне пользовательской CSP до отдельной совместимой миграции его сторонних шаблонов.

## 2026-09-11 Воспроизводимая цепочка сборки

- Базовый Python image и источник бинарника uv закреплены multi-arch digest’ами, а не изменяемыми тегами `slim`/`latest`; обновление digest выполняется отдельным проверяемым коммитом.
- Все сторонние GitHub Actions закреплены полными commit SHA. Комментарий с major-версией сохраняет читаемость и возможность контролируемого обновления.
- Публикуемый application tag может оставаться `latest` как указатель релиза; исполняемые входы самой сборки обязаны быть неизменяемыми.

## 2026-09-11 Аудит Python-зависимостей

- После frozen sync CI проверяет фактически установленную `.venv` официальным PyPA pip-audit через OSV; проверка не разрешена как advisory/allow-failure.
- Сам GitHub Action закреплён SHA релиза v1.1.0. Исключения уязвимостей не заданы: каждое будущее исключение требует отдельного обоснованного решения.
- Контрольный querybatch OSV по текущему окружению не вернул известных уязвимостей на момент проверки; это временный снимок, поэтому CI повторяет аудит для каждого PR.

## 2026-09-11 Virtual application project

- Django-приложение запускается из checkout в CI и из `/app` в контейнере; распространяемый wheel для него не создаётся. `tool.uv.package = false` делает этот фактический контракт явным.
- `uv sync --frozen` устанавливает только зафиксированные runtime/dev зависимости и больше не загружает Hatchling для editable build. Docker-контракт `--no-install-project` остаётся эквивалентным.

## 2026-09-11 Непривилегированный container runtime

- Gunicorn, миграции и scheduler выполняются от фиксированных UID/GID 10001; root используется только на этапе сборки image для установки файлов и назначения владельца каталогов.
- Каталоги `media` и `exchange` создаются с владельцем приложения до объявления volumes. Одноразовый `volume-init` с root-правами приводит новые и существующие mounts к UID/GID 10001 и завершается до старта web; постоянные сервисы root не получают.
- PostgreSQL Compose image закреплён multi-arch digest так же, как Python и uv. `JWT_AUDIENCE` явно передаётся web и scheduler из окружения Compose.

## 2026-09-11 Адаптивная таблица журнала

- Семантическая HTML-таблица сохраняется для desktop и assistive technology; на ширине до 720 px CSS представляет те же строки как карточки, не дублируя серверную разметку данных.
- Подписи мобильных полей берутся из единого описания `JOURNAL_COLUMNS` через `data-label`, поэтому персональная настройка состава колонок остаётся согласованной с карточками.
- Правый sticky-статус полезен только при достаточной ширине и отключается до 1280 px: на tablet пользователь получает честную горизонтальную прокрутку без перекрывающего слоя.

## 2026-09-11 Liveness и readiness

- Liveness намеренно не обращается к внешним зависимостям и доказывает только работу Django HTTP-процесса; readiness отдельно доказывает соединение с основной БД.
- Docker healthcheck использует readiness, потому что именно healthy-состояние web открывает запуск scheduler. Redirect больше не считается успехом probe.
- Ответ 503 не содержит исключение или параметры БД; диагностические подробности остаются в server logs.

## 2026-09-11 Lifecycle production-сервисов

- `unless-stopped` выбран вместо `always`: аварийное завершение и reboot восстанавливают сервис, но явная остановка оператора сохраняется.
- Gunicorn становится основным процессом контейнера после одноразовых миграций через shell `exec`; это сохраняет последовательность старта и корректную обработку SIGTERM master-процессом.
- Scheduler реализован как Python management-команда, а не shell-loop: signal handler прекращает новые циклы, текущий `run_tasks` получает время завершиться, временная ошибка журналируется и повторяется на следующем интервале.

## 2026-09-11 CI least privilege

- Workflow не изменяет репозиторий и публикует image в Docker Hub по отдельным credentials, поэтому встроенному `GITHUB_TOKEN` достаточно `contents: read`.
- `persist-credentials: false` исключает сохранение token checkout в локальной конфигурации git, где его мог бы прочитать последующий build step.
- Service images считаются частью исполняемой цепочки CI и обязаны быть закреплены digest так же, как production images и Actions SHA.

## 2026-09-11 PostgreSQL connection pool

- Pool включён только в production; development и тесты сохраняют простой persistent connection для предсказуемости транзакционных тестов.
- При pool `CONN_MAX_AGE` обязан быть нулём: Django закрывает request connection, фактически возвращая физическое соединение psycopg в pool. Health check выполняется самим pool перед выдачей.
- Максимум 4 соединения на процесс даёт верхнюю границу 16 для штатных трёх Gunicorn workers и scheduler; изменение лимита требует сверки с PostgreSQL `max_connections`.

## 2026-09-11 Fail-safe parsing production environment

- Security-sensitive booleans не используют правило «всё неизвестное равно false»: неоднозначность конфигурации является startup error.
- Wildcard `ALLOWED_HOSTS=*` запрещён даже для закрытого корпоративного ресурса; закрытый контур не заменяет проверку Host header. Leading-dot host pattern остаётся допустимым для явно выбранного доменного суффикса.
- Нулевой HSTS допускается для контролируемого первичного внедрения, но отрицательное, нечисловое или чрезмерное значение запрещено.

## 2026-09-11 Ротация container logs

- Локальная ротация обязательна независимо от наличия централизованного log collector: сбой или недоступность внешнего получателя не должен превращаться в исчерпание диска application host.
- Фиксированный профиль 10 МБ × 5 выбран как безопасный базовый предел для одного узла; увеличение выполняется вместе с capacity plan и внешним хранением логов.
- Сжатие применяется только к ротированным сегментам и не меняет чтение текущего потока через `docker compose logs`.

## 2026-09-11 Browser-origin contract token login

- Полный Django CSRF token нельзя требовать от независимого server-to-server клиента, поэтому endpoint остаётся `csrf_exempt`; exemption компенсируется отдельной проверкой browser provenance до любых side effects.
- Наличие `Origin` имеет приоритет и требует точного совпадения с текущим либо явно доверенным origin; `Sec-Fetch-Site: cross-site` без Origin также запрещён. Отсутствие обоих заголовков допускается для небраузерной интеграции.
- Trusted SSO origins отделены от общего `CSRF_TRUSTED_ORIGINS`, чтобы разрешение token exchange не расширяло доверие ко всем state-changing формам портала.

## 2026-09-11 Cache policy динамических ответов

- Закрытый контур и авторизация не делают proxy/browser cache безопасным для ПДн; динамическая поверхность использует fail-closed `no-store` независимо от роли и кода ответа.
- Политика централизована в middleware, чтобы новый endpoint автоматически наследовал её, а ранний redirect/error не обходил заголовок.
- Fingerprinted static assets исключены: они не содержат пользовательских данных и должны сохранять эффективное immutable-кеширование WhiteNoise.

## 2026-09-11 Явная auth route surface

- Подключение полного набора стандартных Django auth URL считается публикацией функций, даже если продукт не показывает ссылки на них; каждый такой endpoint обязан иметь утверждённый UX и operational backend.
- Email reset не публикуется без корпоративного SMTP/identity contract. Пароли и блокировки управляются администратором согласно существующей модели закрытого ресурса.

## 2026-09-12 Одноразовый schema lifecycle

- Изменение схемы является отдельной deployment-фазой: Compose запускает один `migrate` после готовности PostgreSQL, а `web` зависит от его успешного завершения.
- Gunicorn больше не выполняет миграции в startup-команде. Это отделяет повторный запуск приложения от schema write и не допускает гонку нескольких web replicas.
- `migrate` наследует тот же non-root, read-only, no-new-privileges и cap-drop профиль, что постоянные application services; ему доступен только bounded `/tmp`.

## 2026-09-12 Неизменяемая идентичность обращения

- `n_irp` является ключом межсистемного upsert и фиксируется после первого создания записи; пользовательское редактирование не является операцией смены идентичности.
- Поле остаётся в форме как читаемый контекст, но Django `disabled` связывает его с исходным instance и игнорирует подмену POST на сервере.
- Импорт сохраняет право находить существующую запись по `n_irp`; controlled importer обновляет содержимое и provenance, но не переименовывает ключ записи.

## 2026-09-12 Безопасный admin-export обращений

- Технический admin-export считается самостоятельной поверхностью выгрузки и не может полагаться на sanitizer отчётного модуля.
- Перед сериализацией любой строковый cell Dataset проходит общий `excel_safe_value`; правило применяется также к CSV, поскольку формулы исполняются офисным клиентом после открытия, а не сервером.
- Предметный `EXPORT` записывается после успешной генерации bytes, но до возврата response. Ошибка обязательного аудита не передаёт файл пользователю.

## 2026-09-12 Единая tenant-граница отчётности

- Владение обращением во всех read-path определяется неизменяемой организацией `employee_one`, как в журнале, карточке, печати и защищённых файлах.
- `otv_kon` описывает текущую ответственную организацию и может меняться при маршрутизации, поэтому не является authorization boundary.
- Фильтр по `otv_kon` применяется только внутри уже ограниченного owner-scope и не может расширить доступ СМО.

## 2026-09-12 Непустой ключ обращения

- Пустая Excel-ячейка и строка только из whitespace имеют одинаковую семантику отсутствующего `n_irp`; Excel-канал генерирует новый UUID, как при физически пустой ячейке.
- Общий ФЛК считает whitespace-only обязательные значения незаполненными, поэтому они не доходят до модели как формально truthy строки.
- DB constraint запрещает пустой/пробельный ключ независимо от write-path. Legacy-значение нельзя безопасно выдумать задним числом, поэтому migration останавливается с ID записей для ручной сверки.

## 2026-09-12 Целостность условных реквизитов обращения

- `zh_d` имеет смысл только для вида «Жалоба» (`irp_type=2`); иные непустые сочетания отклоняются одинаково импортом, model validation и БД.
- `date_cross` и `time_cross` не могут существовать без `pr_out`, а время направления — без даты. Обязательность даты для каждого значения `pr_out` не вводится без утверждённого Приложения 10.
- Противоречивые legacy-реквизиты не очищаются автоматически: migration останавливается с ID записей, поскольку удаление таких сведений требует предметной сверки.

## 2026-09-12 Атомарный аудит изменений пользователей в Django Admin

- Общий HTTP event подтверждает запрос, но не заменяет предметное событие изменения учётной записи: middleware выполняется после завершения внутренней транзакции Admin.
- `EmployeeAdmin` пишет предметный `CREATE`/`UPDATE` после сохранения M2M-ролей, оставаясь внутри atomic change form; отказ аудита откатывает и поля, и права.
- Массовая разблокировка повторно выбирает весь набор под `select_for_update` и фиксирует каждое событие в одной транзакции. Ошибка не оставляет частично разблокированный batch.

## 2026-09-12 Атомарный аудит permission-набора роли

- Каноническую роль нельзя создать, удалить или переименовать через Admin; изменение её permissions остаётся отдельной привилегией superuser.
- Предметный `UPDATE` записывается после фактического `save_m2m` внутри штатной atomic change form Django Admin.
- Ошибка обязательного события откатывает замену всего permission-набора, поэтому эффективные права участников роли не меняются без доказательного следа.

## 2026-09-12 Атомарный CRUD-аудит изменяемых справочников

- Темы обращений и категории новостей остаются управляемыми через Django Admin, но каждое создание, изменение и удаление получает предметное событие с точным model label и PK.
- Одиночные change/delete используют штатную транзакцию Admin; общий mixin пишет событие до её завершения, поэтому отказ аудита откатывает модель.
- `delete_selected` оборачивается отдельной общей транзакцией: удаление всего набора и все предметные события либо фиксируются вместе, либо полностью откатываются.

## 2026-09-12 Явный HTTP-контракт read-only экранов

- Реестры, карточки, печатные представления, подсказки и списки служебных модулей являются безопасными read endpoints и принимают только GET/HEAD.
- POST/PUT/PATCH/DELETE отклоняются декоратором до object lookup и предметной логики; mutation endpoints сохраняют свои явные POST либо GET/POST контракты.
- HEAD сохраняет безопасную семантику: формирует метаданные ответа, но не увеличивает пользовательский счётчик просмотров новости.
- Проверка ведётся по полной runtime-матрице portal URL, а не только по наличию декоратора в исходнике.

## 2026-09-12 Граница privilege fields в EmployeeAdmin

- Наличие `change_employee` не даёт права назначать `is_superuser` или прямые Django permissions: для любого non-superuser эти поля серверно исключаются из ModelForm как readonly.
- Действующий superuser может управлять privilege fields другой учётной записи для технического восстановления и контролируемой настройки Admin; собственные access fields остаются неизменяемыми через UI.
- Роли приложения остаются канонической бизнес-RBAC моделью; прямые Django permissions не влияют на capability policy портала.

## 2026-09-12 Атомарный аудит административной смены пароля

- Стандартный password endpoint Django Admin является отдельным credential write-path и не проходит через `save_model`/`save_related` сотрудника.
- POST формы выполняется в явной транзакции; предметный `UPDATE` создаётся только при фактическом изменении password hash и откатывает credential при собственной ошибке.
- Audit target содержит только PK и вид операции: пароль, password hash и иные секреты не записываются ни в target, ни в detail.

## 2026-09-12 Защита superuser от делегированного EmployeeAdmin

- `change_employee` разрешает обслуживать обычные учётные записи, но не делегирует управление корневым principal.
- Password endpoint доступен только действующему superuser; non-superuser не видит superuser-строки в admin queryset, поэтому direct URL и bulk action также не получают объект.
- Object-level `has_change_permission` остаётся второй серверной границей на случай вызова Admin API с уже разрешённым объектом.

## 2026-09-12 Детерминированный мультиролевой контекст

- Capability policy и UI используют полный набор канонических групп пользователя; административная навигация не зависит от того, какая M2M-строка вернулась первой.
- Пользовательская подпись перечисляет все роли в порядке `ROLE_CHOICES`; legacy `SYSTEM_ROLE` сохраняет первый канонический код для совместимости.
- Superuser без бизнес-группы получает явную подпись «Суперпользователь», не изобретая ему роль приложения.

## 2026-09-12 Tenant scope в Django Admin

- Прямые Django permissions не отменяют организационную границу: любой non-superuser вне ТФОМС получает только строки своей организации.
- Единый mixin применяется к обращениям, их истории, ответам, вложениям, XML-файлам и журналу обмена; lookup задаётся declarative через связь модели.
- Обычный staff ТФОМС и superuser сохраняют межорганизационный обзор. Superuser не ограничивается полем `org`, поскольку это технический recovery principal.

## 2026-09-12 Participant ACL в Django Admin

- Диалоги являются participant-scoped данными: Django Admin использует тот же принцип, что portal views, для диалога, темы, ответа и вложения.
- Relation lookup задаётся каждой admin-моделью, а общий mixin добавляет фильтр по текущему principal и `distinct()` для M2M join.
- Superuser не получает неявный доступ к содержимому переписки; для технического просмотра его явно включают в participants, оставляя это изменение наблюдаемым в данных.

## 2026-09-12 Организационная граница EmployeeAdmin

- Прямые Django permissions для non-ТФОМС staff действуют только внутри собственной организации и не дают права создавать principal в произвольной СМО.
- `org` становится readonly для такого actor, а независимый object-level guard отклоняет foreign object даже при прямом вызове permission API.
- Staff ТФОМС сохраняет межорганизационные add/change/view возможности; управление superuser и password endpoint остаётся исключительно за superuser.

## 2026-09-12 Конфиденциальность EventLog в Django Admin

- Для non-ТФОМС staff событие относится к организации через `EventLog.user.org`; чужие IP, targets и details не возвращаются admin queryset.
- События без actor считаются общесистемными и не показываются отдельной СМО, поскольку надёжной tenant-привязки у записи нет.
- Staff ТФОМС и superuser сохраняют полный audit/recovery view, включая межорганизационные и system events.

## 2026-09-12 Tenant-safe related filter IrpAdmin

- Варианты фильтра «Принял» выводятся не из глобального Employee manager, а из уже ограниченного `IrpAdmin.get_queryset(request)`.
- Lookup показывает только principals, связанные с доступными строками, и использует имя без дополнительных запросов на каждый вариант.
- Фильтрация по подставленному ID применяется к тому же scoped queryset и не может расширить tenant boundary.
- Значение query parameter принимается только как ASCII decimal PK не меньше единицы; любое malformed значение fail-closed возвращает пустой queryset вместо 500 или сброса к более широкой выборке.

## 2026-09-12 Глобальный report scope superuser

- Report builders сохраняют существующий integer organization contract; web boundary передаёт `TFOMS` как маркер глобального scope для любого superuser.
- Форма фильтров учитывает `is_superuser` отдельно от profile `org`, поэтому root principal видит полный список организаций.
- Обычный пользователь СМО по-прежнему ограничен immutable owner organization и не может расширить scope параметрами фильтра.
- Login/logout подключены явно с прежними именами, поэтому декораторы, redirects, шаблоны и аудит не меняют публичный контракт.
