## Журнал выполнения

### 2026-09-11 — исходная точка остаточного плана

- Функциональный backlog закрыт кроме требований, зависящих от отсутствующих приложений к ТЗ.

- Следующий контрольный результат: этап 1, доступность и сообщения об ошибках форм.

### 2026-09-11 — этап 1: доступность форм

- Общий клиентский слой связывает label с первым рабочим контролом `.field`, не требуя ручного дублирования логики во всех шаблонах.
- Help text и серверные ошибки включаются в `aria-describedby`; ошибочные поля получают `aria-invalid`, динамическая ошибка — `role=alert` и удаляется из accessible description после исправления.
- AX-дерево формы создания обращения подтверждает доступные названия полей и обязательность; синтаксис JS и Django system check проходят.
- Следующий этап: матрица viewport/theme/font-scale для ключевых маршрутов.

### 2026-09-11 — этап 2: визуальная матрица

- Добавлен воспроизводимый Chrome DevTools прогон `scripts/visual_qa.mjs`, не требующий npm-зависимостей и использующий только локальную QA-учётную запись.
- Проверены 11 ключевых маршрутов в шести размерах окна: 694×869, 1024×768, 1280×800, 1366×768, 1440×900 и 1920×1080.
- Для 694, 1024 и 1920 дополнительно проверены тёмная тема и увеличенный шрифт; всего выполнено 132 сценария.
- Автоматическая проверка не обнаружила переадресаций на вход и горизонтального переполнения документа. Выборочно просмотрены мобильная форма, тёмная таблица задач и сообщения с увеличенным шрифтом.
- Следующий этап: матрица ролей и состояний, начиная с доступов и пустых/заполненных представлений.

### 2026-09-11 — этап 3: роли и системные состояния, итерация 1

### 2026-09-11 — этап 5: вторичный UI debt, итерация 1

- Удалено дублирование JavaScript-подтверждений из экранов новостей; обработка `data-confirm` теперь едина для всего портала.
- Подтверждения добавлены к удалению документов и заметок, а также к блокировке пользователя; уже существующие удаления новостей используют тот же механизм.
- После подтверждённой отправки активная кнопка блокируется, получает `aria-busy` и понятную подпись «Отправка…», что предотвращает повторные POST. При возврате из browser back-forward cache состояние корректно восстанавливается.
- Следующая итерация: перенос оставшихся значимых inline-стилей и обработчиков в общие CSS/JS-компоненты.

### 2026-09-11 — этап 5: вторичный UI debt, завершение

- Печать, возврат и повтор запроса переведены на декларативные `data-ui-action` и единый обработчик без inline JavaScript.

### 2026-09-11 — итерация полировки формы обращения

- На живом экране выявлены контекстно неприменимые поля: классификация жалобы показывалась для любого вида обращения, а дата и время направления — при отсутствии переадресации.

- Визуальная перепроверка выявила конфликт общего `display:flex` с HTML-атрибутом `hidden`; CSS-контракт исправлен и покрыт регрессией. Мобильный снимок и AX tree согласованно показывают свёрнутый блок и доступное раскрытие.

- CheckConstraints закрепляют допустимый lifecycle-статус, плановый срок не раньше поступления и дату закрытия не раньше поступления.
- `Irp.clean()` сообщает пользователю отдельную ошибку обратного планового срока до обращения к БД; ограничение БД защищает импорт, ORM и административные сценарии.
- Перед включением ограничений migration нормализует legacy-строки: неизвестный статус становится `registered`, а обратные даты выравниваются по дате поступления.

### 2026-09-11 — организация сотрудника как tenant-инвариант

- `Employee.org` закреплён CheckConstraint по реестру PRD: 81000/81001/81007/81008; direct ORM/SQL больше не создаёт пользователя вне определённой области данных.
- Legacy-учётные записи с неизвестным кодом сначала деактивируются и только затем технически переводятся в 81000, исключая расширение доступа во время миграции.
- Независимые тесты временного токена переведены с вымышленного 81004 на реальный 81008; auth-семантика не изменилась.

### 2026-09-11 — однократная архивация входящего обмена

- XML/users и Excel используют один helper перемещения в архив: атомарный `os.replace` на одном томе, `copy2` + удаление источника только при системной ошибке `EXDEV`.
- После успешной cross-filesystem копии файл исчезает из `exchange/in`, поэтому следующий scheduler-run не импортирует его повторно и не создаёт второй протокол/ImportLog.
- Ошибки доступа и носителя пробрасываются без ложного fallback; источник при этом остаётся для диагностики и повторного запуска после устранения причины.

### 2026-09-11 — одноразовый обмен временного JWT

- Каждый временный токен получает обязательный уникальный UUID в claim `jti`; проверка также требует `sub`, `aud`, `iat` и `exp`.
- Успешный exchange атомарно сохраняет `jti` с датой истечения. Уникальный первичный ключ закрывает replay и гонку между несколькими web-worker.
- Первый запрос создаёт сессию, повторный запрос тем же токеном возвращает 403 без сессии. Просроченные записи потребления очищаются без сохранения самого JWT.
- Аудитория больше не зашита в token helper: выпуск и проверка используют `JWT_AUDIENCE`, а несовпадающий `aud` отклоняется библиотекой JWT.

### 2026-09-11 — безопасный и согласованный экспорт

- XLSX-экспорты отчётов и журнала событий централизованно нейтрализуют формульные префиксы в пользовательских строках.
- Пользовательский текст PDF экранируется до передачи в ReportLab `Paragraph`, поэтому не может стать внутренней разметкой.

### 2026-09-11 — TLS-граница production

- Django production settings распознают HTTPS по перезаписанному доверенным proxy заголовку `X-Forwarded-Proto`.
- Порт Gunicorn в Compose по умолчанию привязан к loopback, поэтому клиент не может обойти TLS-терминатор и передать приложению поддельную схему.
- `.env.example` больше не отключает secure cookies и HTTPS redirect при копировании в production; документирована безопасная схема отдельного proxy-хоста.

### 2026-09-11 — границы рабочих вложений

- Политика видеороликов до 200 МБ ограничена библиотекой эксплуатационной документации и больше не распространяется на обращения, сообщения и задачи.
- Рабочие вложения используют отдельный model-level валидатор: только документы и архивы из allowlist, не более 20 МБ.
- File picker задач, сообщений и обращений синхронизирован с сервером; удалена ложная поддержка CSV.

### 2026-09-11 — tenant scope карточки обращения

- Первичный исполнитель фиксируется при регистрации и больше не изменяется через edit POST; именно его организация определяет область видимости записи.

- ТФОМС сохраняет межорганизационный выбор, необходимый для централизованной обработки и маршрутизации.

### 2026-09-11 — terminal state темы сообщений

- Закрытая тема теперь блокирует ответ на сервере, а не только скрывает форму в HTML.
- Guard выполняется до валидации и сохранения, поэтому прямой POST не создаёт сообщение, вложение или ложное SEND-событие аудита.

### 2026-09-11 — обязательный период отчёта

- Требование PRD о периоде перенесено с одного JavaScript на серверную форму: хотя бы одна граница периода обязательна для preview и экспорта.
- Direct GET без периода больше не запускает полную выборку; export возвращает 400.

### 2026-09-12 — сквозной контракт runtime-политик

- Compose теперь передаёт `MAX_FAILED_LOGIN_ATTEMPTS` и `SESSION_COOKIE_AGE` из `.env` в web и scheduler; ранее задокументированные настройки молча игнорировались контейнером.
- Production fail-fast ограничивает попытки входа диапазоном 1–10, а восстановление зависших задач — 300–86400 секундами.
- Регрессии проверяют отклонение нулевых, чрезмерных и нечисловых значений, допустимые переопределения и наличие всех параметров в Compose.

### 2026-09-12 — защита собственного административного доступа

- Запрет self-block распространён с отдельной кнопки на серверную форму редактирования пользователя.
- Активный администратор не может отключить собственную запись или снять с себя роль «Администратор»; попытка возвращает понятную ошибку и не изменяет БД.
- Ограничение отражено непосредственно в форме, а управление другими сотрудниками и передача полномочий сохранены.

### 2026-09-12 — единая ролевая политика Django Admin

- Employee Admin больше не предлагает произвольные Django-группы: выбор ограничен зарегистрированными ролями приложения.
- Совместимость роли с организацией проверяется теми же кодами ролей, что и основной портал; например, роль ТФОМС нельзя назначить сотруднику СМО.
- При редактировании собственной записи критичные access-флаги, группы и точечные разрешения доступны только для чтения, поэтому Django Admin не обходит защиту self-lockout.

### 2026-09-12 — неизменяемая идентичность канонических ролей

- Стандартный GroupAdmin заменён защищённым представлением только семи ролей приложения; посторонние Django-группы не попадают в административный список.
- Создание, удаление и переименование канонической роли запрещены, поскольку серверная capability policy опирается на стабильное имя группы.
- Изменение технических Django permissions оставлено только суперпользователю; обычный staff не может расширить административную поверхность роли.

### 2026-09-12 — неизменяемые audit/provenance-записи

- Общий admin mixin запрещает add/change/delete и переводит все поля доказательной записи в readonly.
- Контракт EventLog распространён на протоколы ImportLog, метаданные XmlFiles, IrpHistory и TaskRun; списки и фильтры остаются доступны для расследований.
- Registry-регрессия проверяет права и полный набор readonly-полей всех пяти моделей, а Django system check подтверждает корректность admin-конфигурации.

### 2026-09-12 — единый аудит Django Admin

- Удалено исключение, из-за которого успешные изменяющие `/admin/**` запросы не попадали в EventLog; ошибки admin и раньше фиксировались, теперь покрытие симметрично.

- Интеграционные тесты выполняют реальное создание категории через admin, реальный password login и logout и проверяют actor, result и тип события в едином журнале.

### 2026-09-12 — журнал только через бизнес-lifecycle

- Irp, IrpAnswer и IrpFile в Django Admin переведены в view-only: прямые add/change/delete больше не обходят переходы статуса, tenant scope и IrpHistory портала.

- Registry-регрессия расширена на все три portal-managed модели; существующие экранные тесты подтверждают сохранение штатного редактирования в журнале.

### 2026-09-11 — системный lifecycle задач

- Статус задания стал read-only в пользовательской форме и меняется только фактическим запуском, завершением или recovery; поддельный `running` больше не может вывести задачу из scheduler навсегда.
- При переходе в ручной режим сервер очищает скрытый интервал расписания.
- Новое назначение ограничено активными сотрудниками; существующее назначение деактивированного сотрудника остаётся видимым для безопасного переназначения.

### 2026-09-11 — целостность журнала обмена

### 2026-09-11 — целостность системного аудита

### 2026-09-11 — non-root runtime

### 2026-09-11 — адаптивный реестр без цветной полосы

### 2026-09-11 — readiness основной базы

- `/healthz` оставлен лёгкой liveness-проверкой процесса; новый `/readyz` выполняет минимальный `SELECT 1` через основной Django connection.
- Ошибка БД преобразуется в непрозрачный HTTP 503 без утечки текста исключения; оба endpoint запрещают кеширование и исключены из бизнес-аудита.
- Compose больше не принимает 301/302 за healthy: внутренний probe передаёт доверенную схему HTTPS и требует точный HTTP 200 от `/readyz`, поэтому scheduler зависит от фактической доступности web и PostgreSQL.

### 2026-09-11 — управляемый lifecycle контейнеров

- db, web и scheduler получили `restart: unless-stopped`, поэтому восстановление после crash/reboot не зависит от ручного `docker compose up`.

- Бесконечный shell-loop scheduler заменён management-командой `run_scheduler`: она обрабатывает SIGTERM/SIGINT, ждёт завершения текущего цикла, не дрейфует на shell sleep и повторяет работу после временной ошибки.

### 2026-09-11 — минимальные права и воспроизводимость CI

- Workflow задаёт только `contents: read`, а checkout не сохраняет credential в git config рабочего каталога job.
- Обе job ограничены 30 минутами; concurrency отменяет устаревший run того же ref, предотвращая накопление зависших или уже неактуальных проверок.

### 2026-09-11 — production pool PostgreSQL

- Обязательный `psycopg-pool` теперь реально используется через нативный backend Django: `CONN_MAX_AGE=0` возвращает соединение после запроса, `CONN_HEALTH_CHECKS=True` проверяет его перед повторной выдачей.
- Размер pool по умолчанию ограничен 1–4 соединениями на процесс; connect/pool wait ограничены тремя секундами, idle/lifetime — 300/1800 секундами.
- Все настраиваемые числовые параметры проверяются при startup; отрицательные, нечисловые значения и `min > max` останавливают production до приёма трафика.

### 2026-09-11 — fail-safe security environment

- Production больше не интерпретирует неизвестное булево значение как `False`: secure cookie, HTTPS redirect и proxy trust принимают только явный закрытый набор значений.
- `ALLOWED_HOSTS` обязан содержать конкретные host names; пустой список, `*`, схемы, пути, query/fragment и пробелы запрещены до запуска Django.
- HSTS проверяется как целое число в диапазоне 0–63072000 секунд; опечатка или отрицательное значение дают понятный `ImproperlyConfigured`.

### 2026-09-11 — ограничение container logs

- Все четыре Compose-сервиса используют единый `json-file` logging anchor, исключающий расхождение политики между web, scheduler и PostgreSQL.
- Активный сегмент ротируется при 10 МБ, хранится не более пяти сегментов на сервис, архивные сегменты сжимаются.
- Локальный несжатый верхний предел составляет около 200 МБ для всего stack; диагностика расхода и LogPath добавлена в эксплуатационную инструкцию.

### 2026-09-11 — защита token exchange от login-CSRF

- CSRF exemption сохранён для server-to-server интеграции, но браузерный POST теперь проверяется по `Sec-Fetch-Site` и `Origin`, с Referer fallback для совместимости.
- Same-origin проходит автоматически; отдельная SSO-подсистема допускается только через точный HTTPS allowlist без credentials/path/query/fragment.
- Cross-site запрос отклоняется до decode/consume, поэтому не создаёт сессию и не делает валидный одноразовый `jti` непригодным. Все ответы endpoint, включая 400/403, имеют `no-store`, `no-referrer` и корректный `Vary`.

### 2026-09-11 — запрет кеширования динамических ответов

- Единый middleware назначает `no-store, no-cache, max-age=0, private`, `Pragma: no-cache` и просроченный `Expires` всем динамическим ответам независимо от status и content type.
- Контракт покрывает анонимный redirect, 403/404/500, HTML-карточки, XLSX/PDF и защищённые FileResponse; отдельным view больше не нужно помнить о заголовке.
- `/static/` исключён из middleware и остаётся под fingerprint/cache policy WhiteNoise. Reverse proxy обязан сохранять application cache headers.

### 2026-09-11 — минимальная auth-поверхность

- Широкий include `django.contrib.auth.urls` заменён явными LoginView и LogoutView; существующие route names, шаблон входа, audit и POST-only logout сохранены.
- Неиспользуемые password reset/change/confirm endpoints больше не рендерят Django Admin UI и не создают скрытую зависимость от ненастроенного SMTP.
- Корпоративный сброс пароля и разблокировка остаются административным процессом ТФОМС; все удалённые URL покрыты 404-регрессией.

### 2026-09-11 — отзыв активной сессии при блокировке

- Auth backend проверяет состояние сотрудника не только при вводе пароля, но и при каждом восстановлении пользователя из web-сессии.
- Если сохранённый user id больше не соответствует доступной учётной записи, middleware выполняет logout и удаляет session credential; последующая разблокировка не оживляет старую сессию.
- Регрессия воспроизводит полный путь: действующая сессия, административная блокировка, redirect на вход и отсутствие `_auth_user_id` в session.

### 2026-09-11 — ограниченный срок web-сессии

- Production больше не наследует 14-дневный срок Django: по умолчанию сессия завершается после восьми часов бездействия и при закрытии браузера.
- `SESSION_SAVE_EVERY_REQUEST` реализует sliding idle timeout; активная работа продлевает срок, бездействующая session истекает.
- `SESSION_COOKIE_AGE` проверяется при startup в диапазоне 300–43200 секунд; опечатка и выход за безопасные пределы останавливают запуск.

### 2026-09-11 — адрес клиента в обязательном аудите

- Доверие включено только в production и конфигурируется строгим boolean; dev/tests по умолчанию игнорируют произвольный forwarded header.
- Принимается ровно один синтаксически корректный IPv4/IPv6. Список адресов и мусор безопасно оставляют сетевой адрес proxy, не позволяя выбрать удобный первый элемент цепочки.

- Unit-регрессии покрывают объём, число элементов, traversal и broken ZIP; интеграционная — нулевые строки/изменения БД и корректное завершение importer lifecycle.

### 2026-09-12 — согласование tmpfs с video upload

- Compose ratchet и runtime `df` подтверждают фактическую ёмкость; эксплуатационная инструкция запрещает уменьшать tmpfs ниже продуктового лимита.

### 2026-09-12 — потоковый предел multipart upload

- Первый Django upload handler отклоняет общий `Content-Length` свыше 201 МБ до multipart parser, затем проверяет заявленный part length и фактический offset каждого chunk; после 200 МБ он вызывает `StopUpload(connection_reset=True)`, закрывающий temporary file без дочитывания остатка.
- Middleware принудительно завершает multipart parsing до прикладного view и возвращает HTTP 413; AuditMiddleware фиксирует неуспешный POST, а модель/БД не изменяются.
- MemoryUploadHandler исключён: допустимые файлы сразу пишутся в ограниченный `/tmp`, количество файлов в одном request ограничено одним. Малый-limit integration test и полные upload-регрессии подтверждают контракт.

### 2026-09-12 — атомарные имена файлов обмена

- Ручная загрузка и запись FLCP больше не разделяют проверку существования и открытие файла: artifact создаётся атомарным режимом `xb`.
- При занятом имени выбирается UUID-суффикс и повторяется эксклюзивное создание; ошибка записи удаляет только частичный файл, созданный текущим writer.
- Детерминированная регрессия синхронно запускает два writer и подтверждает разные пути и полную сохранность обоих payload.
- Архиватор также резервирует destination эксклюзивно до `os.replace`/cross-filesystem copy; параллельная регрессия подтверждает, что два одноимённых источника сохраняются раздельно и удаляются только после успешного переноса.

### 2026-09-12 — приватные права файлов обмена

- Каталоги организаций нормализуются до `0700`, а атомарно создаваемые input/FLCP artifacts — до `0600` независимо от process umask.
- Перед архивированием режим внешнего входного файла принудительно ограничивается `0600`, поэтому `os.replace` и cross-filesystem `copy2` не переносят избыточно открытые права.
- Regression-тесты проверяют фактические POSIX mode bits одновременно записанных и архивированных файлов; невозможность смены режима трактуется как fail-closed filesystem error.

### 2026-09-12 — безопасный production log level

- Subprocess-регрессии подтверждают fail-fast для небезопасных уровней и применение `WARNING` ко всей logger-конфигурации.

### 2026-09-12 — граница доверия reverse proxy

- `TRUSTED_PROXY_IPS` принимает проверенные IPv4/IPv6 CIDR и обязателен при доверии хотя бы одному forwarded header; default ограничен loopback.
- Sanitizing middleware выполняется раньше Django SecurityMiddleware: `X-Forwarded-Proto` от недоверенного peer удаляется до определения scheme, а `X-Forwarded-For` после валидации заменяет только `REMOTE_ADDR` и не передаётся дальше.
- Интеграции подтверждают HTTPS без redirect от доверенного loopback, принудительный redirect при spoofing с внешнего peer и сохранение реального peer IP в обязательном аудите.

### 2026-09-12 — границы временного SSO JWT

- `JWT_TTL` явно передаётся web/scheduler через Compose и в production ограничен диапазоном 30–900 секунд при сохранении штатного значения 300 секунд.
- `JWT_AUDIENCE` валидируется как один стабильный идентификатор длиной до 128 символов, без пробелов, URL и управляющих конструкций.
- Subprocess-регрессии подтверждают fail-fast для многолетнего/отрицательного TTL и malformed audience, а token tests сохраняют контракт выпуска и проверки claims.
- Decode независимо проверяет фактический интервал `exp - iat`: он должен быть конечным, положительным и не превышать `JWT_TTL`. Годовой корректно подписанный token получает 403 до создания web-сессии и записи consumed `jti`.
