## 1. Назначение и границы

Этот документ является независимой проверкой `COMPLIANCE_REVIEW_2026-09-18.md` и планом
закрытия подтвержденных разрывов. Исходный обзор не изменялся. Проверка выполнена по
основному техническому заданию, дополнительному письму, текущему коду, тестам,
production-конфигурации и эксплуатационной документации репозитория.

Исходная кодовая база анализа зафиксирована на `HEAD 4505995`. Ниже отдельно отражено
состояние реализации после параллельного этапа; окончательным доказательством считается
только интегрированный коммит, прошедший приемочные ворота раздела 7.

Классификация работ:

- `code-completable` - результат можно полностью реализовать и доказать в репозитории;
- `requires customer artifacts` - до получения эталона Заказчика невозможно определить
  точное поведение или доказать соответствие;
- `requires deployment-organizational evidence` - код может быть готов, но приемка требует
  целевой площадки, актов, регламентов, испытаний или договорных документов;
- `out-of-scope supplemental` - требование встречается только в методическом письме либо
  добавлено аудитом сверх основного ТЗ; включать в поставку можно только после письменного
  изменения объема.

### 2.1. Покрытие атомарных требований

Указанное в обзоре число `136` не воспроизводится из опубликованной ID-схемы. Диапазоны
`OBJ-00-01` - `OBJ-8-10`, использованные в перечне требований, содержат 152 уникальных ID.
Матрица обзора сворачивает их в 76 строк. Это не означает автоматически, что потеряны 16
требований: число зависит от правила атомизации, но текущая цифра не согласована с
собственными идентификаторами.

Перед формальной приемкой нужен канонический реестр, в котором:

1. один ID соответствует одному проверяемому утверждению;
2. составные требования не получают один общий статус;
3. выводы аудитора помечены отдельно от буквального текста;
4. для каждого ID указаны источник, страница, обязательность, владелец доказательства и

5. итоговое количество вычисляется из реестра, а не вводится вручную.

### 2.3. Подтвержденные разрывы основного ТЗ

1. `OBJ-2.2-10`: ручная форма не использует тот же доменный ФЛК, что XML/XLSX.
2. `OBJ-3.0-02`, `OBJ-3.1-01…02`: часть запрещенных действий видна пользователю и
   завершается ожидаемым серверным 403 вместо отсутствия недоступного элемента интерфейса.
3. `OBJ-3.2-01`: пустой набор видимых колонок не сохраняется как осознанное состояние.
4. `OBJ-3.2-03`: часть таблиц сортирует только текущую DOM-страницу, а не весь набор.
5. `OBJ-3.2-04`: пользователь может фиксировать только первую колонку, а не выбранные
   колонки.
6. `OBJ-3.2-05`: пользовательская группировка колонок не хранится и не применяется.
7. `OBJ-3.4-06`: detail/атрибуты события недоступны как полноценное управляемое раскрытие.
8. `OBJ-3.5-05`: создание групп запрещено и в portal UI, и в прокси-admin.
9. `OBJ-2.2-04`, `OBJ-2.2-06`, `OBJ-2.2-09`, `OBJ-2.5-01…09`: точность нельзя доказать
   без артефактов Заказчика.
10. `OBJ-3.1-24`: соответствие ФСТЭК №17 для ГИС 2 класса не подтверждается одним кодом.

## 5. Зависимости критического пути

```text
R-00 -> формальная приемочная матрица
R-01 -> A-01 -> T-H -> приемка отчетов
R-01 -> A-02/A-03/A-04 -> C-01/T-F -> T-G -> приемка регистрации
R-03 -> A-05 -> T-I -> D-02/T-K -> приемка SSO
R-05 -> D-03/T-K -> приемка защиты ГИС 2 класса
T-A + T-B + T-C + T-D + T-E + T-F -> repository release candidate
repository release candidate + T-G + T-H + T-I -> T-J/T-K
T-J + T-K + D-01/D-07/D-08 -> T-L -> итоговая приемка
```

Главный внешний критический путь - получение Приложений №1–10 и матрицы ФЛК. Без них
можно улучшить архитектуру и закрыть независимые дефекты, но нельзя честно объявить
соответствие девяти отчетов и входного обмена.

## 6. Приемочные ворота

### Gate 1. Requirements baseline

- канонический реестр имеет непрерывные ID и вычисляемый итог;
- для каждого требования выбран ровно один authority source;
- все `S-01…10` имеют письменное решение о scope;
- неоднозначности preview, ролей, XML, XLSX, ФЛК и отчетов закрыты протоколом решения.

### Gate 2. Repository compliance

- `C-01…10` закрыты тестами и трассируются к ID;
- все миграции forward/backward либо явно irreversible с планом восстановления;
- pytest проходит на PostgreSQL 14+;
- lint, migration drift, production check, dependency audit и container runtime gate зеленые;
- browser QA проверяет роли, mobile/desktop, контраст, large text и keyboard-only;
- production registry не содержит моков, `noop` или недоступных пользователю действий.

### Gate 3. Artifact conformance

- официальные XML/XLSX fixtures проходят единый ФЛК во всех четырех каналах;
- девять отчетов совпадают с Приложениями №1–9 по данным и представлению;
- `docs/EXCHANGE_FORMATS.md`, `docs/DATABASE.md` и `docs/USER_GUIDE.md` соответствуют
  release candidate, а не предположениям.

### Gate 4. Staging and security

- реальный IdP/каталог прошел positive, negative, replay, expiry и outage scenarios;
- полный release работает на целевых Linux и PostgreSQL 14+;
- Яндекс Браузер, Chromium-Gost и Chrome проходят единый acceptance pack;
- применимые меры ФСТЭК имеют утвержденные доказательства;
- backup/restore, monitoring, incident и rollback procedures проверены на площадке.

### Gate 5. Contract delivery

- переданы лицензия, immutable дистрибутив и согласованный комплект документации;
- проведены демонстрация и обучение обеих аудиторий;
- подписаны акты этапов и гарантийные условия;
- даты подтверждают соблюдение 5 + 5 и общего 10-дневного срока.

## 7. Приоритет исполнения

1. `P0 external`: `R-00…05`, прежде всего Приложения №1–10 и ФЛК.
2. `P0 code`: `C-01`, `C-02`, `C-03`, потому что они затрагивают единообразие данных,
   права и прямые требования разделов 2.2, 3.0, 3.1 и 3.2.
3. `P1 code`: `C-04`, `C-05`, затем `C-06…10`.
4. `P1 artifact`: `T-G`, `T-H`, `T-I` сразу после получения соответствующих контрактов.
5. `P0 acceptance`: `T-J`, `T-K`, `T-L`; их нельзя заменить unit-тестами репозитория.
6. `Change request only`: любые `S-01…10`.

## 8. Итоговый критерий завершения

Полное соответствие можно заявить только тогда, когда одновременно выполнены четыре
условия:

1. закрыты все подтвержденные `code-completable` разрывы;
2. отчеты, XML, Excel и ФЛК проверены по официальным материалам Заказчика;
3. SSO, целевая платформа, браузеры и меры защиты подтверждены на реальной площадке;
4. комплект поставки, обучение, гарантия, лицензия и сроки подтверждены документами.

До этого корректный статус системы: **функционально развитый кандидат на приемку с
незакрытыми кодовыми, входными и организационными доказательствами**, а не полностью
соответствующая поставка.
